# Visitor confirmation by email reply

Penny receives the existing owner alert immediately at her saved notification email. A separate message asks the visitor to check inbox/spam, move the message to inbox if needed, and reply **CONFIRM** on the first line. The CRM changes **Awaiting email confirmation** to **Email confirmed by reply** only after a signed receiving event and a validated reply. This confirms access to an email address; it is not two-factor authentication, a confirmed booking or marketing permission.

The enquiry stays saved and available to Penny while pending. Conversion to a contact preserves the separate enquiry confirmation status. A reply does not create a contact or change “Waiting for response.” Confirmation is per enquiry, not an assertion that every historical address on a contact is verified. Non-owner staff cannot see verification records in this release.

## Activate on the existing live project

1. In Supabase SQL Editor, run **only** [202610260004_email_confirmation.sql](../supabase/migrations/202610260004_email_confirmation.sql). It is an incremental upgrade for the existing CRM, adds RLS-protected records, and leaves confirmation sending off. Do not rerun `heartara-install.sql` on the existing database.
2. In Resend → Domains, add **reply.heartarahealing.com**, enable **Receiving**, and install the exact DNS records Resend provides for that subdomain. Wait until receiving is verified. Keep the already verified `heartarahealing.com` sender. The separate receiving subdomain avoids changing the main domain’s incoming-mail destination. No mailbox needs to be created for each reply address.
3. In Resend → API Keys, create a server-only key with access to read received emails (Full access if that is the available permission). The existing sending-only key can remain unchanged. Save the new key directly into Vercel as **RESEND_RECEIVING_API_KEY**; never paste it into chat or public website files.
4. In Resend → Webhooks, add `https://www.heartarahealing.com/api/provider/resend-webhook`. Subscribe to **email.received**, **email.delivered**, **email.bounced**, and **email.failed**. If that endpoint already has a webhook, update its subscriptions rather than creating duplicates. Save its signing secret directly into Vercel as **RESEND_WEBHOOK_SECRET**.
5. Add **EMAIL_REPLY_DOMAIN=reply.heartarahealing.com** in Vercel. Keep the existing `RESEND_API_KEY`, `EMAIL_FROM`, and `EMAIL_MODE=resend`. Optionally set a stable random **EMAIL_CONFIRMATION_SECRET** so rotating a provider key does not invalidate outstanding confirmation replies. All secrets are server-only. Set variables for Production and any Preview environment you use, then deploy the latest branch again.
6. Open the newest live `/crm/` → Settings → Visitor email confirmation. Resolve any listed missing configuration, then click **Enable visitor confirmation emails**. This affects new enquiries; existing enquiries get a confirmation only when Penny requests one from their detail page.
7. Submit one clearly labelled test enquiry using an email you control. Verify Penny gets her alert immediately and the enquiry shows “Awaiting email confirmation.” Reply **CONFIRM** to the visitor email. Refresh the enquiry or linked contact: it should show “Email confirmed by reply,” while follow-up status remains unchanged. Check Resend webhook deliveries if it stays pending.

This repository does not automatically provision receiving DNS, install the hosted SQL upgrade or verify real inbox delivery. Adding only an API key does not finish receiving setup. Development tests use synthetic records and fake transport; they send no real mail.

## Sending, retries and operational limits

Enquiries and both email jobs are queued durably in one transaction. Sending happens after the website response; an email outage never discards the enquiry. The existing queue worker sends Penny’s alert first and then eligible visitor confirmations. Delivery/bounce states appear under Settings → Email notifications; provider acceptance is not proof of inbox placement. A delivered message alone never confirms the visitor’s address.

Each reply address contains a unique challenge. The database stores its hash, expiry and confirmation audit metadata, not reply text or attachments. The receiving endpoint verifies Resend’s signature, retrieves the email from Resend’s fixed API endpoint with the receiving key, checks the first line, excludes automatic replies, and requires the sender to match the submitted address. It never downloads attachments or follows links from a message. Resend itself retains received email under its own provider settings.

Challenges expire after seven days. A visitor address gets at most three new challenges per 24 hours, with a 15-minute resend cooldown per enquiry. Repeated provider callbacks are idempotent. Owner-requested retries are available from enquiry details; inactive or expired jobs cannot send a valid challenge. Reviewed contact erasure revokes associated challenges, removes the copied email address and cancels pending confirmation jobs. Rotating a signing key requires requesting a new confirmation for affected pending jobs.

Configure the existing authenticated notification scheduler if automatic recovery during quiet periods is needed. Without it, queued retries run on later submissions or the owner’s **Send queued notifications now** action. A user’s reply only confirms an enquiry; further questions should use the website because this receiving address processes confirmations only.
